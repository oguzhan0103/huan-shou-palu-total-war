# 唯一帕鲁原生交付事务桥纯开发验收

日期：2026-08-22

结论：**P2 已补齐“赎金支付成功后，把同一只唯一帕鲁安全交给玩家”的通用事务桥。容量预检、服务端创建、服务端捕获、固定 individual identity、玩家 Pal 仓库回读、幂等重试、回调确认和世界卸载回滚均已进入源码、运行时、合同与自动测试。Build 24575825 的正式原生适配器绑定仍为 0，因此这是可供内容模块接线的失败关闭底座，不是玩家已经能收到帕鲁的实机完成项。**

## 1. 采用的原生路线

历史 ObjectDump 能看到 `PalPlayerState:GetPalStorage`、`PalIndividualCharacterContainer:FindEmptySlot`、`PalUtility:PalCaptureSuccess` 和 `PalNPCManager:SpawnNPCForServer` 等候选入口，但该 Dump 不是当前 Build 24575825，不能直接升级为正式绑定证据。

公开实现 [AdminCommands 的 spawn.lua](https://github.com/dkoz/AdminCommands/blob/main/AdminCommands/Scripts/modules/spawn.lua) 也采用 `SpawnNPCForServer` 后等待生成 Actor，再调用 `PalCaptureSuccess` 的路线。这只能证明路线有先例；其源码明确把 spawn/catch 标为实验性实现，并没有覆盖本项目要求的容量预检、唯一个体回读、失败回滚和重复交易隔离。因此本项目没有直接复制，而是在候选原生调用外增加严格事务边界。

## 2. 本轮实现

- 新增 `_G.PWFT_UNIQUE_PAL_NATIVE_DELIVERY_BRIDGE_V1`，并把同一实例交给受信内容模块。
- P2 `pal-delivery` 载荷新增 Core 战役定义中的确切 `speciesId`；Provider 必须同时匹配 `uniquePalId` 与 species 白名单。
- 当前 Build 绑定必须显式声明并通过：`currentBuildVerified / serverAuthoritativeSpawn / serverAuthoritativeCapture / capacityPreflight / storageVerification / stableIndividualIdentity`。任何一项缺失都拒绝注册。
- 创建前先检查玩家 Pal 容器容量；如果适配器发现同一 delivery 已交付，可按同一 individual key 恢复，而不是重新生成。
- 创建结果必须返回稳定的 `nativeDeliveryId` 和 `individualKey`。Core 在 Provider 接受后保存两者，最终确认时逐项核对。
- 捕获只提交一次。仓库回读暂未看到同一 individual 时，只重试回读与最终回调，不重复创建、不重复捕获，也不要求玩家再次付款。
- 最终回调同时核对 `deliveryId / providerId / authoritySource / bindingId / worldGeneration / nativeDeliveryId / nativeIndividualKey / palDeliveryKey / uniquePalId / speciesId / playerId`。
- 世界卸载时只回滚“已创建但尚未提交捕获”的临时个体；已经提交捕获的记录不做盲目删除。所有运行时对象引用都由适配器持有，不写入 sidecar。
- 明确禁止直接改 Pal 容器、调试捕获 API 和 Palworld 存档写入。

## 3. 自动测试

- 未核验当前 Build 的适配器失败关闭；
- species 白名单、Provider、目标 binding、route 和 world generation 精确匹配；
- 容量预检后只创建一个个体；
- Core 进入 `awaiting-confirmation` 且 request/individual 都一致后才允许提交；
- 捕获只提交一次，第一次仓库回读未完成后可重试；
- 第二次回读确认同一 individual 后才完成 Core delivery；
