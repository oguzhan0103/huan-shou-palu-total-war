# 原生帕鲁袭击胜负与有限信物回调

日期：2026-08-11
目标 Build：Steam `24467282`

## 结论

小型聚落已经采用实机验收过的四只 `PalNPCManager` 原生角色作为正式攻城实体；本轮又在同一实机事件中完成了“4/4 生成—确定性头领—玩家出战帕鲁击杀归因—4/4 全灭—玩家方胜利—有限信物发放”。状态更新为 **源码完成、自动测试通过、死亡与信物结算实机通过**。

本体 `PalInvaderManager` 的事件创建接口在当前 Build 会返回成功但不产生 incident，因此不再把它作为发布阻塞项或伪报为成功。保留被动兼容监听，正式路线使用同为本体角色系统创建的四只临时攻击者，并由明确的死亡权威事件结算。

## 两条结果来源

`pal_raid_native_binding.lua` 监听四个本体事件：

1. `PalInvaderManager:BroadcastInvaderStart`：建立一次权威袭击记录；
2. `BP_PalIncidentInvaderEnemy:OnCharacterSpawned`：收集波次、成员和确定性头领候选；
3. `BP_PalIncidentInvaderEnemy:OnDeadEnemy`：只接受本地玩家或归属明确的本地出战帕鲁击杀；
4. `PalInvaderManager:BroadcastInvaderEnd`：将胜负和参与证据一次性交给有限信物服务结算。

该监听保留为本体自然事件的兼容路线。

正式发布路线由 `settlement_raid.lua`、`attendance_raid_result_bridge.lua` 和 `pal_raid_result_adapter.lua` 组成：

1. 倒计时结束且玩家在场时，通过 `PalNPCManager.SpawnNPCForServer` 请求四只真实原生帕鲁角色；
2. 四个句柄全部解析为 Actor 后一次性登记事件，固定将第一个登记成员指定为头领；
3. `/Script/Pal.PalCharacter:OnDeadCharacter` 只接收本轮四个 Actor 的死亡；
4. 四个成员必须全部死亡才判玩家方胜利；
5. 只有本地玩家或归属明确的本地出战帕鲁直接击杀头领才发放信物；
6. 玩家缺席、生成不足、超时、清理、归因不明、重复死亡或重复结算都失败关闭，不发信物。

## 本轮实现

新增 `attendance_raid_result_bridge.lua`，将四只临时攻击者作为一个权威事件登记，并把事件、生成、死亡、全灭结算四种 authority 分开。结算不依赖倒计时结束或清理计时器，不会把“事件开始”写成“玩家获胜”。

`pal_raid_native_binding.lua` 对外提供现有 UID/玩家所属帕鲁归因能力；`pal_raid_result_adapter.lua` 同时接受本体 incident 和四角色攻城两类生命周期，但要求各自正确的 authority，来源不能混用。

## 本体 incident 路线的边界

此前三轮诊断确认：QA 热键调用 `PalInvaderManager.StartInvaderMarchForBaseCamp`，并直接调用 visitor/enemy 请求时接口都可返回 `true`，但没有创建 incident、成员或管理器状态。因此不能用返回值冒充一次本体袭击：

```text
NATIVE_DIRECT_VISITOR_REQUESTED ... accepted=true result=true
NATIVE_DIRECT_VISITOR_MISSING ... visitors=0
NATIVE_DIRECT_ENEMY_REQUESTED ... accepted=true result=true
NATIVE_DIRECT_ENEMY_MISSING ... incidents=0 managerInfo=false selectionOverrides=0
```

这条路线保留为将来 Build 兼容入口，不再阻塞当前基座。当前正式路线不会接管场景里原有睡眠帕鲁；四只原生攻击者生成失败即失败关闭。
