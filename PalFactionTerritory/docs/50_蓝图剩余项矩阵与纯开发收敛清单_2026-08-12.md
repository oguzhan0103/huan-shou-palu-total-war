## 1. 结论

当前已经形成一套可展示、可扩展、能够承载内容包的机制基座。A0 至 A9 的纯开发缺口已经收敛：任务目标、保卫战好感、资源存量与战争、唯一帕鲁、城市存亡、NPC 势力态度、结局效果、领主护卫和高难奖励均已有独立运行时、失败关闭边界和自动测试。仍不能把这写成“最初蓝图全部实机完成”，因为其中若干战略机制还需要内容作者提供具体 Actor、势力设定和剧情参数，并在游戏内完成原生 provider 绑定与集中验收。

按本文件第 7 节的 28 个机制工作包计：

- 12 个达到当前 Build 的实机完成，或其本身属于离线作者工具的完成标准；
- 16 个已经完成机制源码与自动测试，仍需内容绑定、原生 provider 或实机；
- 0 个仍停留在只有旧契约、没有本轮对应实现的状态；
- 0 个属于“不需要用户参与但尚未开始”的开发项。

因此有三种不同的“完成比例”，不能混用：

- **已有源码或版本化契约覆盖：28/28，100%**；这表示机制底座均已有可调用落点，不等于 28 项全部实机。
- **加权机制成熟度：约 76%**；公式见第 7 节，剩余约 24% 主要是内容绑定和实机闭环，而不是继续盲写通用状态机。
- **严格实机/工具验收：11/28，约 39%**；它最保守，但会低估无须进游戏的 SDK 和纯状态机价值。

对外最稳妥的说法是：**1.0 开源基座的通用机制开发已经覆盖完整蓝图分母，可以发布给内容作者；距离“所有剧情与具体设定装入后可完整游玩”仍约有四分之一成熟度，主要是内容绑定、原生对象适配和实机验收，不是重新开发商人、攻城、论道、玩家护卫或 A0–A9 状态机。**

## 7. 完成比例的分母方法

### 7.1 为什么不能按 Markdown 复选框计数

旧文档的粒度不一致：一个“城市毁灭”可能包含唯一帕鲁归属、Boss 伤害门闩、Actor 刷新、持久化和结局效果；一个“F5 面板”只是单一入口。直接数复选框会把小功能和大战略模块都算作 1，并且旧待办已经被新证据覆盖。

本审计把蓝图和用户后续决策归并为 28 个可独立验收的机制工作包；剧情正文、已撤出项和明确非 1.0 项不进分母。
