# B7 战略世界统一就绪门闩纯开发验收

日期：2026-08-23

结论：`PASS（纯开发）`；`B7 实机仍未开始`

## 1. 本次完成内容

新增 `strategic_world_readiness.lua`，把原来分散在 A5、A6、A7、P1、P2 和内容模块中的条件收敛成一个统一 B7 门闩。运行时会在内容模块首次加载和每次世界重新激活后重新判定，并输出 `B7_STRATEGIC_WORLD_READINESS` 日志；同一结构化状态也进入 Mod 自有外接状态投影，供操作台显示。

门闩固定检查 9 项：

1. 内容模块已配置、激活且无失败；
2. 至少一只唯一帕鲁和一座城市已由内容包定义；
3. 至少一条结局路线已由内容包定义；
4. 战略原生 Provider 覆盖全部 5 类事件，并同时绑定 `unique-pal`、`city-anchor`、`city-boss`；
5. Boss Provider 覆盖通知、生成、开放、关闭、冷却，并有经过核验的 Boss 绑定；
6. 世界效果 Provider 覆盖战争、保卫、刷新抑制、精确清理、空城、商会过滤、赎金和 Pal 交付，同时有包含刷新器、Actor、城市、商会和原生路线的完整目标绑定；
7. 生产交付与原生交付事务桥都已绑定，继续要求固定 individual identity 且禁止直接改容器；
8. NPC 态度 Provider 已受信并绑定至少一个精确 Actor；
9. 结局 Provider 覆盖称号、世界态度、势力态度和城市迁移，模型仍无确认或提交权。

机器合同为 `contracts/strategic_world_readiness.v1.json`。三个阶段只有：

```text
content-key-required
native-bindings-required
ready-for-b7-live-acceptance
```

即使第三阶段通过，也只代表可以开始实机，不代表已经实机通过，更不代表用户已验收。

## 2. 当前基座的诚实结果

正式 `config.lua` 的 `contentModules.modules` 仍为空，这是“不内置剧情密钥”的既定基座边界。当前离线运行结果为：

```text
ready=false
phase=content-key-required
passed=0
blocked=9
contentBlocked=3
runtimeBlocked=6
liveEvidenceRequired=true
liveAccepted=false
saveWrites=false
```

这不是开发回退，而是门闩首次把 B7 为什么不能直接进游戏拆成机器可读结果：3 项必须由内容作者提供，6 项必须在真实对象发现后由原生集成完成。以后不会再因某个 Provider 数量大于零就误写“已接通”；Provider 必须覆盖该总线的全部能力，世界效果目标还必须含完整城市/清理/商会绑定。

## 3. 自动验证

新增 `strategic_world_readiness_spec.lua`，覆盖：

- 空基座严格返回 `content-key-required`；
- 只有内容时返回 `native-bindings-required`；
- 9 项全部满足时只进入 `ready-for-b7-live-acceptance`，仍保持 `liveAccepted=false`；
- 世界效果 Provider 允许广域 Actor 扫描时重新失败关闭；
- 启动烟测确认全局 API、外接状态和换世界重算均已接线。

同时补强四个既有总线状态：战略原生、Boss、世界效果、结局 Provider 现在都会报告“全能力 Provider”数量；战略绑定按三种 Actor 类型分别计数；世界效果只把含刷新、清理、城市和商会数据的目标计为完整绑定。

专项 Lua 测试、运行时烟测和 `tools/verify_mod0.py` 均通过。本轮没有启动 Palworld、没有部署 QA 开关、没有修改 Palworld 存档，也没有把离线门闩冒充 B7 实机证据。

## 4. 后续顺序

接下来不再新增第二套战略状态机。正确顺序是：

1. 内容作者给出最小战略内容密钥；
2. 只读发现当前 Build 的精确 spawner、Actor、城市锚点、居民/功能 NPC 刷新器和代表 NPC；
3. 注册完整 Provider 与目标绑定，让统一门闩进入 `ready-for-b7-live-acceptance`；
4. 再按 `docs/50` 的 B7 标准集中跑正反分支和恢复检查。
