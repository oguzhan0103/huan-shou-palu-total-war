# 势力商业、持久化、UI 与公共服务开发记录

更新日期：2026-07-28  
适配版本：Palworld 1.0.1 / Steam Build 24181527  
当前状态：**机制与适配边界已完成离线验证并部署；实机验证按用户要求后置**

## 1. 本轮目标

本轮继续建设“粉丝设计任务和剧情后即可直接接入”的机制底座，不制作具体剧情、任务对白或大规模文本。

核心规则保持不变：

- 七个人类势力初始为蓝色友好、未加入，且可以同时加入。
- 五个帕鲁势力初始为红色敌对，不能加入或获得人类身份等级。
- 人类身份为成员、核心成员、领队、领主；领队开始解锁护卫资格。
- 商业只承担有限的好感度辅助增长和敌对关系修复。
- 任务与保卫战仍是主要好感度来源。
- 所有人类势力达到领主后才解锁帕鲁和解。
- 结局三要求所有指定人类势力达到领主，并且所有指定帕鲁势力转为蓝色。
- 当前阶段不实现好感度降低、身份降级或权限回收。

- 非需求品不增加好感度。
- 全局商业窗口额度仍由 `faction_progression.v1.json` 统一限制。

这些数值属于待实机平衡值，不是最终公开承诺。

### 2.3 原生交易桥接

实现文件：

```text
mod0/ue4ss/PalFactionTerritory0/Scripts/pwft/faction_commerce.lua
mod0/ue4ss/PalFactionTerritory0/Scripts/pwft/commerce_bridge.lua
```

购买结算流程：

```text
原生购买请求
  -> 暂存交易
  -> 原生 RecieveBuyResult_ToClient
  -> 仅 Successed / 数值 0
  -> 势力商业额度结算
  -> 事件 ID 防重复
```

失败的原生购买不会增加好感度。内部结算拒绝或异常前也不会提前把交易标记为已完成，因此可以安全重试。

出售方面已经完成以下链路：

- 监听 `/Script/Pal.PalUIItemShopBase:TrySell`。
- 从 `PalItemSlot.ItemId.StaticId` 和 `PalItemSlot.StackCount` 自动提取出售物品。
- 把 UI 出售尝试与后续网络出售请求关联。
- UI 返回失败时清除待结算记录。
- UI 返回成功时只记录“本地 UI 已接受”，不把它误当作服务器结算成功。

当前本体反射证据里仍没有确定的原生“出售服务器成功”回调，因此不会仅根据 `TrySell = true` 或出售请求直接发放好感度。后续原生适配层必须在确认服务器出售成功后调用：

```lua
_G.PWFT_COMMERCE_BRIDGE_V1:confirm_item_sale(...)
```

如果没有成功信号，就不结算。

### 2.5 UI、保卫战与护卫公共服务

实现文件：

```text
mod0/ue4ss/PalFactionTerritory0/Scripts/pwft/faction_ui_model.lua
mod0/ue4ss/PalFactionTerritory0/Scripts/pwft/faction_defense.lua
mod0/ue4ss/PalFactionTerritory0/Scripts/pwft/faction_guard.lua
```

UI 数据模型已经提供：

- 12 个势力的关系、颜色、好感度和身份状态。
- 下一身份进度。
- 商业额度和当前剩余额度。
- 是否允许加入。
- 护卫资格和当前原生提供器状态。
- 帕鲁和解门槛和结局三门槛。

它的当前状态为：

```text
data-model-ready-native-umg-renderer-pending
```

这表示数据层可供后续 UMG 或其他玩家界面直接读取，但尚未宣称已有游戏内可见 UI。

保卫战服务支持：

- 创建防守事件、登记玩家参战、成功或失败结算。
- 玩家与该人类势力敌对时提供仅限本次防守的临时蓝色关系。
- 防守成功可发放好感度。
- 防守失败不降低好感度。

护卫服务支持：

- 按领队/领主身份判断护卫资格。
- 注册原生护卫提供器。
- 部署和召回护卫。
- 通用角色适配器可为七个势力创建原生护卫提供器。
- 护卫生成时记录跟随目标，但原生跟随控制器行为仍标记为
  `native-follow-controller-pending-live-validation`。
- 当前总开关关闭时仍明确返回 `native-guard-provider-pending`，不会伪造已生成结果。
